# Small-model alignment: SFT and DPO on Qwen2.5-0.5B

This is my work for PA2 of the GenAI course. The assignment takes a small pretrained model (Qwen/Qwen2.5-0.5B), fine-tunes it on instruction data, then runs DPO on two different preference datasets, and finally checks whether any of it helped by letting an LLM judge compare the outputs. There is also a smaller side experiment with TRL and LoRA that tries to give SmolLM2-360M-Instruct a "furious chef" persona.

The repo started from the course starter, so the manual is still in `docs/assignment_manual.pdf`. The training loops, DPO loss and batching code are written from scratch (no Hugging Face `Trainer`, no TRL) everywhere except the LoRA task, where TRL is the point.

## Where things are

```text
src/alignment/      batching, log-probs, SFT and DPO losses, prompt template, persona helpers
submission_adapter.py   thin wrappers around src/alignment for the staff grader
scripts/            training, generation, pairing, judging and report-asset scripts
tests/              unit tests (the starter smoke test plus my own edge cases)
notebooks/          the Kaggle notebooks I actually ran, in order, with outputs
eval_sets/          the fixed prompt sets (AlpacaEval-300, HH-eval-300, persona-40, persona held-out-22)
data/persona_lora/  the provided persona preference data
results/            configs, metrics, generations, pair files, judgments (what the report is built from)
report/assets/      tables and figures for the report, generated by scripts/make_report_assets.py
```

Inside `results/`: `sft/`, `dpo_hh/` and `dpo_uf/` have the config, `metrics.jsonl`, summary and data manifest of each run. `generations/` has every model output (with a `.meta.json` next to it holding the decoding settings), `eval/` has the A/B pair files, and `judgments/` has the judged files, their summaries and failure logs. `lora/` has the sweep tables, the training logs of all twelve LoRA runs, and the two committed adapters.

## Setup

On Kaggle (GPU T4 x2), as in notebook 01:

```bash
python -m pip uninstall -y -q torchao || true
python -m pip install -q -r requirements.txt
python -m pip install -q -e . --no-deps
```

`torch` is deliberately not in `requirements.txt`; Kaggle already ships a build that matches the GPU. For a local checkout, install a torch build for your machine first. `kaggle_benchmarks`, which the judge script uses, only exists inside Kaggle's benchmark notebooks.

The reported runs used torch 2.11.0, transformers 4.57.6, datasets 4.8.5, trl 0.25.1 and peft 0.20.0.

## Running the pipeline

The notebooks are the easiest way to follow what I did. 01 is the setup check, 02 the baseline generations, 03 SFT, 04 a behaviour check of the SFT model, 05 and 06 the two DPO runs, 07 the first LoRA sweep, 08 generation and pair building, 09 the judging, 10 to 12 the second LoRA sweep and its judging, and 13 and 14 repeat the two main comparisons with a repetition penalty and retry the few verdicts the judge failed to return. The judge notebooks need Kaggle's model proxy.

The same steps as plain commands (defaults match the guide configuration, so most flags can be left out):

```bash
python scripts/make_alpaca_subset.py
python scripts/build_sft_data.py --out_dir outputs/data
python scripts/build_dpo_data.py --dataset hh --out_dir outputs/data
python scripts/build_dpo_data.py --dataset uf --out_dir outputs/data

python scripts/train_sft.py --train_path outputs/data/sft_train.jsonl --val_path outputs/data/sft_val.jsonl --run_dir outputs/sft
python scripts/train_dpo.py --sft_path outputs/sft/best \
    --train_path outputs/data/dpo_hh_train.jsonl --val_path outputs/data/dpo_hh_val.jsonl --run_dir outputs/dpo_hh

python scripts/generate.py --model_path outputs/sft/best --tokenizer_path Qwen/Qwen2.5-0.5B \
    --prompts_path eval_sets/alpaca_eval_300_seed42.json --output_path outputs/generations/sft_alpaca300.json \
    --generator qwen2.5-0.5b-sft --max_new_tokens 512

python scripts/build_pairs.py --test_path <dpo generations> --ref_path <sft generations> \
    --test_name dpo_uf --ref_name sft --prompts_path eval_sets/alpaca_eval_300_seed42.json \
    --out outputs/eval/dpo_uf_vs_sft_alpaca300_pairs.jsonl --prefix uf

python scripts/judge_pairwise_kaggle.py --pairs_path <pairs file> --output_path <judged file> \
    --judge_model google/gemini-3.6-flash --batch_size 5 --sleep_seconds 5 --max_retries 3 --reuse_judgments
```

DPO expects the policy on `cuda:0` and the frozen reference on `cuda:1`. The judge script can be tried without any network using `--judge_model mock`. `scripts/retry_unknown_judgments.py` re-judges only the pairs that came back unknown and keeps the original call counts.

For the LoRA task, `scripts/train_lora_dpo.py` trains one adapter (`--rpo_alpha 1.0` adds the NLL term on the chosen answer), `scripts/generate_chat.py` generates with it, and `scripts/persona_sweep_tools.py` builds the sweep tables, style statistics and the adapter selection.

To rebuild the tables and figures for the report from the committed results:

```bash
python scripts/make_report_assets.py
```

## What came out

SFT validation loss went from 1.350 to 1.323 in one epoch. Against the SFT model, as scored by Gemini through the Kaggle proxy:

| comparison | wins / ties / losses | win rate without ties |
|---|---|---|
| DPO-HH on the HH eval | 137 / 70 / 93 | 0.596 |
| DPO-UF on AlpacaEval | 94 / 60 / 146 | 0.392 |

So the HH model looks better on the safety prompts, while the UltraFeedback model came out worse than its own SFT starting point on AlpacaEval. A large part of that second result turned out to be repetition. With greedy decoding about 40% of SFT outputs and 60% of DPO-UF outputs on AlpacaEval contain a repeated phrase, and the judge penalises those. Repeating both comparisons with a repetition penalty of 1.1 (same models, prompts and judge) cut the repeated-phrase outputs to 33 and 63 of 300, and the UltraFeedback result moved from 94 / 60 / 146 to 121 / 57 / 122, a tie. The HH advantage stayed (133 / 71 / 96, 0.581) and the win rate is similar whether the HH model's answer is shorter, longer or about the same length as SFT's (0.60, 0.59 and 0.55 without ties, each on fewer pairs). In the main greedy numbers the HH win came almost entirely from pairs where its answer was shorter, so the report goes through both settings.

The persona experiment was mostly a negative result. An adapter that stays coherent shows no persona, and the adapter with a clear persona is significantly worse on usefulness and safety. The sweep tables are in `results/lora/` and `report/assets/`.

## Things to know

The SFT and DPO checkpoints are about 1 GB each and are not in git. They live in the output of Kaggle notebooks 03, 05 and 06 (`outputs/sft/best`, `outputs/dpo_hh/best`, `outputs/dpo_uf/best`). The generations, pair files and judgments that every table is built from are all committed, so the reported numbers can be reproduced without retraining. The two LoRA adapters that are committed under `results/lora/final_adapter/` are small enough to keep in git, but `*.safetensors` is ignored by default, so they were added with `git add -f`.

The main results use greedy decoding with 512 new tokens and no repetition penalty, identical for every model, so that no model gets a decoding advantage. Many outputs end in repeated phrases under those settings, which is why the penalty rerun above exists; it is a sensitivity check, not a replacement for the main numbers.

Three judge verdicts never came back (the proxy returned empty replies for a threat-rewrite prompt and a hateful-insult request, even after retries). They are excluded from win rates, logged in the `.failures.jsonl` files, and none are in the two headline comparisons.
