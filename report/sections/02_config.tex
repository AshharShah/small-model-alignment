\section{Experimental Configuration}
\label{sec:config}

Table~\ref{tab:config} lists the configuration of the four submitted checkpoints. I generated every value in it from the files each run saved (its configuration, its summary, and its generation settings) instead of quoting the guide defaults, so the table shows what I actually used. I trained on Kaggle's two T4 GPUs. SFT and the LoRA adapter each used one, and the DPO runs put the policy on one GPU and its frozen reference on the other. Training took 79 minutes for SFT, 51 for HH-RLHF DPO, 70 for UltraFeedback DPO, and about one minute for the LoRA adapter.

SFT and both DPO runs share the optimizer (AdamW with $\beta=(0.9,0.95)$), gradient clipping at 1.0, a 512-token maximum length, and seed 42. SFT ran one epoch of 937 steps at an effective batch of 32 (2 sequences times 16 accumulation steps), with a peak learning rate of $2\times10^{-5}$, 3\% warmup, and cosine decay. Both DPO runs started from the best SFT checkpoint, which also served as their frozen reference, and used a fixed learning rate of $1\times10^{-6}$, $\beta=0.1$, and an effective batch of 32 (one pair times 32 accumulation steps) for 468 steps. For SFT, the best validation loss (1.323) came at the final step, so I kept that checkpoint. For each DPO run I kept the checkpoint with the highest validation reward accuracy: step 400 of 468 for HH-RLHF (0.644, against 0.636 at the end) and the final step for UltraFeedback (0.706).

The LoRA run differs more. The manual allows TRL and PEFT for this one task, so I trained the adapter on SmolLM2 with TRL's \texttt{DPOTrainer}: rank 16, $\alpha=32$, dropout 0.05, on all seven linear projections, which adds 8.68 million trainable parameters (2.34\% of the model's 370.5 million). I used a higher peak learning rate ($5\times10^{-5}$ with cosine decay), a smaller effective batch of 16, and 3 epochs (39 steps). I also added a negative log-likelihood (NLL) term on the chosen answer to the DPO loss, to raise the likelihood of that answer.

\paragraph{Generation.} I decoded greedily for every evaluation (\texttt{do\_sample=False}), so temperature and top-p never applied. Each model could generate up to 512 new tokens, with a repetition penalty of 1.0, a length penalty of 1.0, and no n-gram blocking. Within each comparison I kept these settings identical for SFT and DPO, so the judge compares models and not decoding strategies. The Qwen runs use the Alpaca-style template from Section~\ref{sec:data}, and the SmolLM2 runs use the model's chat template. The only exception was the decoding sensitivity check in Section~\ref{sec:results}, where I repeated two comparisons with a repetition penalty of 1.1 for both models.
